# ADR-0062: User Guide

**Status:** Proposed
**Date:** 2026-11-16
**Author:** Jovan

## Context

OpsClear's target users are non-technical owners of 5–50 person businesses, and there's no self-service how-to for them. Someone who signs up has to work out alone how to set up an organisation, bring in their team and start tracking work.

This ADR adds a written user guide inside the app. The first version covers the onboarding journey plus a page for each main feature area, following the breakdown ADR-0049 already defined: 24 pages and an index. It's the last milestone of PRJ-014 on purpose, so it can describe the verification flow, invite emails and preferences delivered earlier in the phase.

Promoted from JOB-240 (Future Consideration, PRJ-002) into PRJ-014 / MIL-046. This ADR is JOB-336.

### Facts from the existing system that shape this design

- **No docs tooling exists.** `docs/` only contains `dev/`. The `docs/docs/` folder the idea mentions doesn't exist, and there's no Docusaurus or static-site build.
- **The frontend already renders Markdown** with `react-markdown` + `remark-gfm` (notes), and has public routes (`/`, `/features`) served by the same nginx as the app. A guide inside the SPA needs no new build or deploy.
- **Tailwind v4 with `@tailwindcss/typography` is already installed and enabled** (`@plugin "@tailwindcss/typography"` in `src/index.css`), so the `prose` classes are available. Build: Vite 7 with `@vitejs/plugin-react`.
- **`/features`** (ADR-0040) shows prospective users interactive demo slides, one card per feature: the "what". There's no "how".
- **The golden-path E2E spec** (`frontend/cypress/e2e/golden-path/golden-path.cy.ts`, ADR-0049 §6 / Appendix §26) drives almost the same story through the real UI with dedicated `uniqueEmail('golden-*')` users and API helpers (`orgApi.ts`) for setup: create an org, accept an invite, change statuses, notes, approvals, dashboard. Cypress's `specPattern` is `cypress/e2e/**/*.cy.ts`, so a spec outside `e2e/` doesn't run in CI.
- **There's no Help entry in the app.** The user menu has Overview, Feedback and the rest. First-run empty states use the shared `EmptyState` component (ADR-0041), e.g. on `ProjectListPage`.
- **The app is bilingual** (en/sr, ADR-0037), with the language in the user's preferences (ADR-0023, server-synced from ADR-0061).
- **PR templates** exist (`.github/pull_request_template.md`), and `pr-reviewer` reviews every PR against the process docs (ADR-0054).
- **Flows this guide depends on are being built in this phase:**
  - email verification: MIL-043, JOB-344
  - invite emails, Copy link and Resend: JOB-345
  - Mine filter and due-soon highlight: JOB-353
  - preferences: MIL-045 (JOB-351 to JOB-354)
  - ID prefixes: MIL-044, JOB-349
  - API-key rate limit and the 429 toast: MIL-042 (JOB-337, JOB-339)

  The screenshots and text for those pages must come after those land.

## Decision

- **Public `/guide` pages in the SPA**, in **English and Serbian**. They look like a professional docs site but are built from small libraries inside the existing UI:
  - MDX pages (`@mdx-js/rollup`) with our own guide components
  - `prose` typography
  - heading anchors and an "On this page" list (`rehype-slug` + `rehype-autolink-headings`)
  - search in the browser (`minisearch`)
  - screenshot zoom (`react-medium-image-zoom`)
  - a docs layout we build in the app
- **The first guide has 24 pages plus an index, in five sidebar sections:** Getting started (the onboarding journey), Daily work, Planning, Admin & settings, and Account & more.
- **Screenshots are generated by Cypress specs,** one per sidebar section, with fixed sample data. They run on demand, not in CI.
- **The guide is linked from:**
  - a "Help & guide" entry in the user menu
  - the public nav and footer
  - "How does this work?" links on the key first-run empty states
  - cross-links with `/features` in both directions
- **Keeping it current is a process rule:** a PR that changes a documented flow updates the guide. A coverage map tells `pr-reviewer` which screens each page documents, so it can flag PRs that touch them without a guide change.

## Technical design

### Database, API, Backend

None.

### Content (`frontend/src/guide/`)

```
frontend/src/guide/
  pages.ts                 # ordered page list: section, slug, title key, coverage globs, related /features card
  components/              # Steps, Step, Callout, Screenshot, RoleBadge, FeatureLink (MDX components)
  en/00-index.mdx … en/24-faq.mdx
  sr/00-index.mdx … sr/24-faq.mdx
frontend/public/guide/
  en/<slug>-<n>.webp       # generated screenshots
  sr/<slug>-<n>.webp
```

- **Pages are MDX:** Markdown plus guide components, compiled at build time by `@mdx-js/rollup` (added to `vite.config.ts` before the React plugin, with `remark-gfm`, `rehype-slug` and `rehype-autolink-headings`). Each page module also exports its `frontmatter` (`title`, `description`) and the list of headings for the "On this page" list.
- **Loading:** pages are loaded lazily per page with `import.meta.glob('./{en,sr}/*.mdx')`, so the guide doesn't grow the main bundle.
- **Guide components** (in `components/`, passed through an `MDXProvider`):
  - `<Steps>` / `<Step>`: numbered steps with a vertical line
  - `<Callout type="tip|note|warning">`
  - `<Screenshot src alt caption>`: wraps `react-medium-image-zoom`; alt text required
  - `<RoleBadge role="Owner|Admin|Member">`: "who can do this"
  - `<FeatureLink card="…">`: "See it in action" to `/features`

  Plain Markdown images still work; `<Screenshot>` is preferred.
- **Writing style:** short numbered steps (`<Steps>`), plain language, bold for the exact button labels as they appear in the app in that language. No internal terms (ADR, jOOQ, etc.).
- **`pages.ts` is the coverage map.** For each page it lists the app files the page documents, as globs, e.g. `invite-team` → `src/features/org/OrgInvitesPage.tsx`, `src/features/org/AcceptInvitePage.tsx`, `keycloak/themes/opsclear/login/register.ftl`. `pr-reviewer` reads it.

### Frontend

- **Routes:** public `/guide` (the index) and `/guide/:slug`, outside `RequireAuth`, like `/features`. An unknown slug redirects to `/guide`.
- **`GuideLayout`**, a three-column docs layout built with our existing components and Tailwind:
  - the public nav when logged out, the app header when logged in
  - **left:** a search box plus the page list grouped into the five sections (collapsible headings), current page and section highlighted (a drawer on mobile)
  - **centre:** the page in `prose dark:prose-invert max-w-none` with our heading and link colours
  - **right** (desktop only): a sticky **"On this page"** list built from the page's headings, highlighting the section in view (`IntersectionObserver`)
  - **bottom:** previous/next links
- **`GuidePage`:** loads the MDX module for the slug in the app language, falling back to English with a "Not yet translated" note. It renders inside `MDXProvider` with the guide components and sets the page title from the frontmatter. A language switch on the page changes the app language preference, the same as everywhere else.
- **Search (`minisearch`):**
  - built in the browser from the plain text of the current language's pages (title, headings, body), loaded on first focus of the search box
  - results show the page title and the matching heading, and go straight to that anchor
  - plain text comes from a build-time `?raw` import of each `.mdx`, with MDX/JSX tags stripped
  - no server, no external service
- **Dependencies added:** `@mdx-js/rollup`, `@mdx-js/react`, `rehype-slug`, `rehype-autolink-headings`, `minisearch`, `react-medium-image-zoom`. `remark-gfm` and `@tailwindcss/typography` are already there.
- **Entry points:**
  - **User menu:** "Help & guide" → `/guide`.
  - **Public nav and footer:** "Guide" → `/guide`.
  - **`EmptyState`** gets an optional `helpLink` (`{ to, label }`), used on:
    - `ProjectListPage` with no projects → `first-project`
    - the job list with no jobs at all → `create-job`
    - `OrgMembersPage` when the owner is alone → `invite-team`
  - **`/features` cards** get a "How to use it" link when a guide page names that card.
- **i18n:** en and sr keys for the guide's UI chrome (nav, sidebar, prev/next, "See it in action", "How does this work?"). Page content lives in the Markdown files, not in i18n JSON.
- **Page title** via `usePageTitle`, e.g. "Invite your team · Guide".

### Screenshots (`frontend/cypress/guide/guide-screenshots.cy.ts`)

- **Outside `cypress/e2e/`,** so CI's `specPattern` doesn't pick it up. It runs with `npm run guide:screenshots` (`cypress run --spec cypress/guide/** --config screenshotsFolder=…`), once per language (`GUIDE_LANG=en|sr`).
- **One spec file per sidebar section** (`getting-started.cy.ts`, `daily-work.cy.ts`, `planning.cy.ts`, `admin-settings.cy.ts`, `account.cy.ts`), so a section's screenshots can be refreshed on their own (`npm run guide:screenshots -- --section planning`).
- **Each uses its own dedicated `uniqueEmail('guide-*')` users and sample org,** reusing the golden-path and `orgApi.ts` helpers for setup that isn't being shown:
  - **Getting started:** the Keycloak register and verify pages, the email through Mailpit (ADR-0059), creating the org, inviting a teammate and their accept page, a project, a job, the three job paths
  - **The other sections:** API-seeded data rich enough to show each screen with realistic content (milestones with progress, a recurring schedule, related jobs, notifications, stats history), then UI-driven screenshots of the screens each page documents
  - **Subscription and API keys:** screenshots of the sample org's real subscription state and of the API key list. No live Paddle call, and no real key value shown: the key is masked or a fake one is used.
- **Readable data:** the org, project, people and job names come from fixed sample data (e.g. "Acme Plumbing", "Kitchen refit"), never seed or customer data.
- **Capture:** `cy.screenshot` of a named element (or the viewport) at a fixed desktop viewport (1280×800), with time-dependent text (dates) fixed using `cy.clock`. A small post-step converts the files to WebP and copies them to `frontend/public/guide/<lang>/<slug>-<n>.webp` with the names the pages use.
- **Refreshing:** re-run the script (all sections or one) and commit the changed images. The spec failing (a selector moved) is itself a signal that the guide needs a look.

### Keeping it current (process)

- **FRONTEND.md:** a new "User guide" section. A PR that changes a screen or flow listed in `src/guide/pages.ts` updates the matching guide page (en and sr) and re-runs `npm run guide:screenshots` if the screen's look changed. New user-facing features don't need a guide page until a guide for their area is planned.
- **PR template:** a checkbox: "Guide: this PR doesn't change a flow in `src/guide/pages.ts`, or the guide is updated."
- **`pr-reviewer`:** for frontend PRs, check changed files against the coverage globs in `pages.ts`. If any match and no file under `src/guide/` or `public/guide/` changed, raise a finding naming the guide page. It's a finding, not a CI failure: sometimes a change doesn't affect the guide, and the author says so.

### Constraints & edge cases

- **Dependencies on this phase:**
  - `sign-up` needs JOB-344; `invite-team` needs JOB-345
  - `finding-jobs` needs JOB-353 (Mine, due-soon)
  - `preferences` needs JOB-351 to JOB-354
  - `organisation-settings` needs JOB-349 (ID prefixes)
  - `api-keys` and `faq` mention the rate limit and its toast (JOB-337, JOB-339)

  Those pages' screenshots and text wait for them; the guide shell and the other pages don't.
- **Paid features:** several pages cover add-on features (notes, approvals, relationships, links, history, templates, recurring, stats). Each shows a `<Callout>` saying it needs an add-on, linking to `subscription`. The screenshot sample org has every add-on.
- **SEO:** the SPA renders on the client, so search engines index the guide only partially. Acceptable for V1, since the guide is for people already arriving at the app.
- **Missing translation:** a missing Serbian page falls back to English, with a small "Not yet translated" note.
- **MDX is code:** pages can import components, so they're reviewed like code. Only the guide components are passed to pages, and pages don't import anything else.
- **Search index size:** about 25 pages per language, so building the index in the browser on first use is instant. Past about 100 pages, it could be built at build time instead.
- **Screenshot size:** about 100 images per language (~4 per page). They're WebP, cropped to the element shown, and aimed at ~60 KB each, about 12 MB for both languages. The copy step fails if any image is over 150 KB.
- **Role differences:** some steps are only possible for the Owner or an Admin (inviting, creating projects, settings). Each page says who can do it with `<RoleBadge>`, and `roles-permissions` has the full table.
- **Demo vs guide:** `/features` slides use mock data; the guide uses real screenshots. They're cross-linked, not merged.
- **Keycloak pages** (register, verify) are screenshotted like any other page. The spec runs against local Keycloak with the opsclear theme.

## Alternatives considered

### Separate docs site: Starlight, Docusaurus or VitePress (decided against)

These give a polished docs look out of the box. Starlight (Astro) could even be served at `/guide` by the existing nginx through an extra Docker build stage.
- **Against:** a second framework and build, a look that's close to but not the app's, and no shared login header or language preference (it would be passed in the URL).
- **Why the in-app stack wins:** it reaches a comparable docs feel (sidebar, "On this page", search, zoom) with small libraries inside the existing UI. If the guide grows to dozens of pages with versioning needs, the MDX content can move to Starlight later with little change.

### Fumadocs UI kit inside the app (decided against for now)

A ready-made React docs layout. It started on Next.js and has adapters for other React setups. It would save building the layout, but its fit with our Vite + React Router SPA is unproven and it brings its own styling to reconcile with ours. The layout we need is small enough to build. Worth trying if later guides need more docs features.

### In-app guided tour (decided against)

It's the most likely to be seen, but it's a much bigger build: overlay, step engine and per-step anchoring. It also breaks quietly whenever the UI changes. It could come later on top of the guide's content.

### English only first (decided against)

Half the writing, but Serbian-speaking owners are a core audience and the app is already bilingual.

### Manual screenshots, or none (decided against)

Manual screenshots go stale without anyone noticing. No screenshots makes the guide much harder for non-technical owners to follow. Generated screenshots can be refreshed with one command.

### Logged-in only (decided against)

People stuck before or during sign-up (e.g. at email verification) are exactly who needs the guide.

### A rule in the docs only, or periodic reviews (decided against)

ADR-0049 notes that stale docs fail without anyone noticing. A reviewer check driven by the coverage map catches drift when the PR is reviewed; a rule alone relies on memory.

### Merge the guide into `/features` (decided against)

`/features` sells to prospects with short demos; the guide teaches existing users step by step. They have different audiences and depths, so they're cross-linked instead.

## Consequences

### Positive

- New owners can get from sign-up to working jobs without help, and every main feature has a how-to page.
- The FAQ answers the most likely support questions before they're asked.
- No new infrastructure. The guide ships, deploys and is translated like the rest of the app.
- Screenshots can be refreshed with one command, and the review check catches drift.
- New pages plug into the same structure: add MDX files and a `pages.ts` entry.

### Negative

- Every change to a documented flow now includes updating the guide text in two languages, and sometimes re-running the screenshot spec.
- About 200 screenshots (~12 MB) in the repo, refreshed occasionally.
- 25 pages × 2 languages is real writing work up front, and the guide covers most screens, so the upkeep rule will fire on many frontend PRs.
- Partial SEO because of client-side rendering.

### Neutral

- FRONTEND.md, the PR template and the `pr-reviewer` agent definition gain a guide rule.
- Deeper per-feature guides (beyond one page per area) can be raised as Future Considerations when users ask for them.
